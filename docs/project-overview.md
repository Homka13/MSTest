# LMS Upload Portal — опис проєкту

Портал приймання навчальних матеріалів для навчального сервісу: структуроване подання матеріалів тренінг-менеджерами, розбір листів від зовнішніх постачальників, парсер тестів і черга ручної валідації.

[[_TOC_]]

## Призначення

Навчальні матеріали надходять від брендів і тренерів хаотично: листами на персональні адреси, з пересиланнями в кілька рівнів, посиланнями на чужі Google Drive, вкладеннями впереміш із логотипами підписів і звітами Teams. Кожен матеріал доводиться вручну знаходити, перейменовувати, класифікувати за брендом і типом та вкладати в навчальну платформу.

Рішення закриває це двома каналами, що зводяться в один каталог.

**Канал А — портал самообслуговування** для внутрішніх тренінг-менеджерів. Тип, бренд і метадані задаються структуровано вже на вході, тож проблема знімається в джерелі, а не розбирається постфактум.

**Канал Б — розбір пошти** для зовнішніх постачальників, яких не змусиш заповнювати форму. Автоматичний парсинг вхідних листів, витяг вкладень і посилань, класифікація, черга на ручну валідацію.

## Автентифікація та каталог Entra

### Окремий каталог для зовнішніх користувачів

Портал працює на **власному каталозі Microsoft Entra External ID (CIAM)**, окремому від корпоративного каталогу організації.

| Параметр | Значення |
|---|---|
| Назва каталогу | `KnowlageUploadPortal` |
| Тип | Microsoft Entra External ID (CIAM) |
| Tenant ID | `819577b9-6a41-43a1-af35-c48622760ad9` |
| Домен входу | `KnowlageUploadPortal.ciamlogin.com` |
| Регіон | EU |

Сенс окремого каталогу в тому, що зовнішні тренери й представники брендів реєструються **в ньому**, а не в корпоративному каталозі. Вони не отримують корпоративного облікового запису, не з'являються в адресній книзі організації й не мають доступу ні до чого, крім порталу. Периметр компанії не розширюється.

### Реєстрація гостьових користувачів і вхід за одноразовим кодом

Вхід відбувається за **одноразовим кодом на пошту (Email OTP)**, без пароля:

1. Користувач вводить свою зовнішню адресу — будь-яку, включно з публічними поштовими сервісами.
2. Каталог надсилає на неї одноразовий код і створює обліковий запис у `KnowlageUploadPortal`.
3. Користувач вводить код і потрапляє в портал.
4. При першому вході показується екран згоди на запитувані дозволи.

Пароля не існує взагалі — немає ні його зберігання, ні скидання, ні ризику витоку. Відкликання доступу — видалення користувача з каталогу.

### Реєстрація застосунку

App Registration створено **в тому самому каталозі**:

| Параметр | Значення |
|---|---|
| Назва | `KnowlageUploadPortal OTP` |
| Application (client) ID | `483ad8a5-ad99-460c-8a4e-de7cf724b494` |
| Тип платформи | SPA (Single-page application) |
| Redirect URI | origin порталу (`http://localhost:5173` для розробки) |
| Дозволи | `openid`, `profile`, `offline_access` |

Microsoft Graph (`User.Read`) навмисно **не запитується**: для користувачів External ID він недоступний, а ім'я та пошту застосунок бере з ID-токена. Екран згоди при першому вході можна прибрати для всіх, видавши admin consent на рівні каталогу: **Enterprise applications → KnowlageUploadPortal OTP → Permissions → Grant admin consent**.

### Налаштування в коді

Уся конфігурація — у `src/authConfig.ts` (44 рядки), значення підставляються зі змінних середовища:

| Змінна | Призначення |
|---|---|
| `VITE_AZURE_CLIENT_ID` | Application (client) ID |
| `VITE_AZURE_TENANT_ID` | **GUID** каталогу, не домен `*.onmicrosoft.com` |
| `VITE_AZURE_CIAM_DOMAIN` | Домен входу CIAM, напр. `KnowlageUploadPortal.ciamlogin.com` |

Токени кешуються в `sessionStorage`: зникають із закриттям вкладки й не залишаються на диску. Повторний вхід зазвичай тихий — каталог тримає власну сесійну cookie, тож код повторно не запитується, доки та сесія жива.

> **Типова помилка налаштування.** CIAM-каталоги обслуговуються **лише** на домені `<tenant>.ciamlogin.com`. Спроба входу через звичайний `login.microsoftonline.com` доходить до сторінки входу і відхиляється **вже після** введення одноразового коду з помилкою `AADSTS500208: The domain is not a valid login domain for the account type`. Виглядає як збій редіректу, хоча причина — домен входу. З тієї самої причини каталог треба вказувати GUID-ом: доменна форма вмикає маршрутизацію за доменом, яка для зовнішніх облікових записів не працює.

## Функціональні модулі

### Форма подання матеріалу

Структуроване подання: назва продукту, імпортер / бренд-дистриб'ютор (обов'язкове поле з `<datalist>` підказками), тренер / автор тренінгу (автозаповнення з облікового запису Entra ID або ручне введення), тип матеріалу, мова, дата події, посилання на зовнішній контент із перевіркою доступу, файли. Нормалізоване ім'я файлу показується живим прев'ю ще до подання. Підтримується режим розбору `.eml`: укинутий лист автоматично заповнює поля форми розпізнаними значеннями.

### Парсер тестів

Формат: `N. Питання`, далі варіанти з маркерами `(!)` — правильний і `(?)` — неправильний.

Обробляє BOM на початку файлу, кілька правильних відповідей на питання, багаторядкові формулювання, відсіює службові рядки Word («Начало формы» / «Кінець форми») обома мовами. Валідація не відхиляє файл, а видає попередження: питання без правильної або без неправильної відповіді, розриви в нумерації. Правила парсингу винесені в конфігурацію — маркери й регулярку можна змінити без правки коду.

### Класифікація та нормалізація

Довідник брендів з варіантами написання (`ЕА`, `GA`, `ADGH`, кирилиця й латиниця), словник маркерів типів із пріоритетами, визначення мови із суфіксів імені файлу, витяг дати події та назви продукту. Кожен матеріал отримує оцінку впевненості; нижче порогу 75 він автоматично потрапляє в чергу на ручну перевірку.

Нормалізоване ім'я: `{Бренд}_{Продукт}_{Тип}_{Мова}_{РРРР-ММ-ДД}.{розширення}`. Оригінальне ім'я зберігається окремим полем.

### Витяг і перевірка доступності посилань

Розгортання захисних обгорток Proofpoint (v1 та v2 `urldefense`), автоматична діагностика доступності Google Drive (через прев'ю-зображення) та YouTube (через oEmbed API), розпізнавання корпоративних UNC-шляхів (`\\server\share\...`). Для посилань з обмеженим або внутрішнім доступом присвоюється статус `PendingAccess` («Очікує доступу») з можливістю підтвердження модератором у черзі перевірки.

### Сповіщення в Microsoft Teams

Інтеграція через Incoming Webhook / Power Automate Workflows. При надходженні нового матеріалу формується структурована адаптивна картка MessageCard із метаданими, імпортером, тренером, статусом посилання та прямими кнопками переходу до матеріалу або в портал.

### Рольова модель (Entra ID App Roles)

Розмежування прав між зовнішніми користувачами (роль `trainer`) та адміністраторами (роль `Admin` / `LMS.Admin`). Тренери мають доступ лише до форми завантаження та парсера тестів, тоді як черга перевірки та довідники приховані та захищені від несанкціонованого доступу.

### Фільтрація службових вкладень

Чотири правила: чорний список за SHA-256, шаблони імен інлайн-зображень підпису, поріг розміру зображень, поріг розміру файлу проти трекінг-пікселів. Звіти відвідуваності Teams і списки учасників не відкидаються, а виділяються в окремі категорії — це матеріали з персональними даними, режим їх зберігання узгоджується окремо.

### Дедуплікація

П'ять ключів по черзі: `file_id` Google Drive, SHA-256 вмісту, зовнішній URL, UNC-шлях, нормалізоване ім'я. Для Drive ключем є саме `file_id`, а не повний URL — параметри `usp=sharing` і `usp=drive_link` дають різні рядки для одного файла. Кожен збіг повертає причину текстом.

### Черга валідації

Фільтр за статусами, роздільне відображення тренера та імпортера, індикатор та дія «Доступ підтверджено» для `PendingAccess`, редагування метаданих, переведення матеріалу в опубліковані або відхилені.

::: mermaid
stateDiagram-v2
    [*] --> Received
    Received --> Parsed
    Parsed --> UnderReview
    UnderReview --> Published
    UnderReview --> Rejected
    Parsed --> PendingAccess
    PendingAccess --> UnderReview: Доступ підтверджено
    PendingAccess --> Rejected: Доступ відхилено
    Published --> [*]
:::

### Керовані довідники

Окрема вкладка для редагування брендів з аліасами, маркерів типів, хешів шуму, внутрішніх доменів організації та параметрів інтеграції Microsoft Teams Webhook. Зміни одразу впливають на роботу системи і зберігаються в репозиторії.

### Що лишається

**Розбір `.eml` несправжній.** Поточна реалізація читає файл як текст і витягує заголовки регулярками. MIME-частини не розбираються, вкладені листи не обробляються, `.msg` не підтримується. Потрібен справжній MIME-парсер із рекурсією.

**Бекенду немає.** Немає ані API приймання файлів, ані спільного каталогу. `localStorage` — це тимчасове рішення для пілоту.

**Канал пошти не розпочато.** Заблокований організаційним питанням: потік досі йде на персональні адреси, тригер поставити нікуди.

**Три рішення поза кодом**, які визначають найближчий фронт робіт: чия shared mailbox, Dataverse чи SharePoint для каталогу, і цільовий формат експорту тестів.

Детальна черга робіт з етапами, залежностями та посиланнями на код — у `TASKS.md` в корені репозиторію.

## Локальний запуск

```bash
npm install
```

```bash
npm run dev
```

Портал підніметься на `http://localhost:5173`. Змінні середовища — у `.env` (шаблон у `.env.example`). Vite читає `.env` лише під час старту, тож після зміни треба перезапустити сервер.

Тести:

```bash
npm test
```

## CI/CD і деплой

Деплой в Azure Static Web Apps через GitHub Actions, тригер — пуш у гілку `main`. Джерела в корені репозиторію, збірка через Oryx, результат у `dist`.

Конфігурація Entra передається у збірку через GitHub Variables (`VITE_AZURE_CLIENT_ID`, `VITE_AZURE_TENANT_ID`, `VITE_AZURE_CIAM_DOMAIN`). Це не секрети — вони й так потрапляють у клієнтський бандл, тому Variables, а не Secrets. Якщо змінна не задана, застосовуються запасні значення з `src/authConfig.ts`.
